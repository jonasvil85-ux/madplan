How the site, the agents and the tools fit together

A public website, built and maintained every day by nine Claude agents that review each other, with a handful of automatic GitHub tools that watch the live site. The team finds and builds every improvement itself. Jonas is the primary user and tries what is new, and he is also the only human who can change the constitution.

Organization chart

Who reports to whom. The Product Owner decides what the team builds and in what order. The QA Reviewer does not report to the Product Owner. It checks everyone's work and is the only one that can merge to main or roll a change back, so the team cannot approve its own work. The Secretary reports to Jonas. Jonas is the user: he tries what is new and says whether it is good or bad, and he alone changes the constitution.

Advisors never build. They find problems and opportunities and write tasks that the Product Owner prioritises. The Second opinion AI is a different AI model (Cloudflare Workers AI). It first acts as the creative one (five different ideas, high temperature) and then as a critic (finds holes, low temperature) on new requirements and designs before they are built. The Product Owner, UX Designer and Security Auditor choose what to use and decide. It only advises. Boxes with a dashed line are planned and do not exist yet.

The platforms in more detail

Git and GitHubSingle source of truth for code, data, agent instructions and workflowsPublic repo jonasvil85-ux/madplan, remote origin. main is production. Work happens on branches named ai/YYYY-MM-DD-topic; only the QA Reviewer merges them, using merge commits so a merge can be undone with git revert -m 1. The Health Monitor deletes branches that are already merged. A branch skaermbilleder holds the latest Browser QA screenshots (one commit, overwritten) so cloud agents can open them. Local clone on Jonas' PC: Desktop\madplan. Files are stored with LF line endings.
VercelHosting, HTTPS, domains, deploysProject connected to the GitHub repo. A change on main is published automatically. The site is plain static files: there is no build command, no server code and no vercel.json. Two domains point at it. The .vercel/ folder is git-ignored. Vercel Analytics needs to be switched on in Vercel to collect visits.

The only agent access is a narrow function for the Product Owner's feedback run: it returns new feedback messages without e-mail addresses and nothing else (scripts/agent_feedback.sql).

Feedback loop: from the chat box to the backlog

The routines in the cloud cannot reach Supabase, so the GitHub Action does the fetching and runs the Product Owner's instructions for this one job. Access to Supabase is a single function protected by a secret that only Jonas knows (scripts/agent_feedback.sql). It cannot see e-mail addresses, users or saved plans. The repository is public, so raw messages are never committed.

Second opinion: a creative AI and a critical agent

Two different jobs are hard to do at once: coming up with something new, and finding the holes. So the second AI is the creative one and the agent is the selector and critic. The model is a different one than Claude (default Llama 3.3 70B on Cloudflare Workers AI, free tier; a stronger model can be chosen), so it has other blind spots. It is an advisor only. Its idea is never a requirement until the agent has chosen it and the Product Owner has put it in the backlog.

How a change reaches production

  1. Product Owner, Security Auditor and SEO and Growth write tasks into ai/BACKLOG.md, each with acceptance criteria.
  2. UX Designer turns the top UX tasks into a design file in ai/design/.
  3. Frontend Developer and Backend Developer build on a branch ai/date-topic and attach a report that proves each criterion. Neither touches main.
  4. QA Reviewer (not the author) runs every test itself, reads the whole diff and picks: merge (class A), stricter validation (class H: prices, quantities, shopping list, meal-plan maths) or reject with a failure report.
  5. A merge to main deploys on Vercel within minutes. Health Monitor and Browser QA then check the live site and write HEALTH.md and BROWSER.md.
  6. Next day the QA Reviewer reads those results first and can revert a merge. The Product Owner checks that the task was really solved and writes a new one if not. The Product Owner also finds the next improvements itself (weaknesses, competitors, new technology) and never waits for Jonas to say what to build.
  7. Secretary writes DAILY.md (ai/DAGENS.md in the repo). Report Mailer turns it into an e-mail to Jonas.
  8. User test by Jonas. When a new feature or a bigger UX change is live and checked, the daily report lists it under "Til prøve hos Jonas" with up to three plain questions: is it intuitive, does it make sense, is it better than before? If Jonas finds it confusing, the Product Owner writes a new task. Passing the QA Reviewer's tests is technical approval; Jonas' answer is user acceptance. Both count.

Two things skip the branch step because they are data, not code: Agent - Data Engineer writes dishes and data straight to main, and Image Generator adds images straight to main.

Roles, secrets and the one human gate

Roles. The AI team owns innovation and development: it finds weaknesses and opportunities, researches competitors and technology, invents features, keeps the roadmap and builds and tests the whole site. Jonas is the primary user and acceptance tester. He answers in plain words whether something is good or bad from a user's point of view, and he is only asked about user-facing choices, never technical ones.

GitHub Actions secrets: CLAUDE_CODE_OAUTH_TOKEN (QA Reviewer run, made from Jonas' private account) and CLOUDFLARE_API_TOKEN (Image Generator). Agents never see or write secrets.

The constitution can only be changed by Jonas: ai/regler.md, ai/agenter/*, .github/, auth.js, feedback.js, privatlivspolitik.html and the routine prompts. Product Owner and Security Auditor may propose changes. Pausing everything: stop the routines on claude.ai and disable the workflows under the GitHub Actions tab.

What the team cannot see

Agents cannot browse the live site themselves; they read the measurements and screenshots from Browser QA. They cannot read user feedback (Supabase) or traffic data (Vercel). Image generation needs a key that only exists in GitHub, so the routines in the cloud never create images.
